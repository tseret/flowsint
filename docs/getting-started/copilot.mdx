---
title: "Investigation copilot"
description: "Review passive enrichment plans for selected entities and summarize their evidence."
---

Select up to ten entities in a sketch and choose **Investigate selected entities**
(the sparkle button in the graph toolbar). Enter an investigation question, then
choose **Suggest a plan**.

The copilot reads the selected entities, a bounded set of nearby relationships,
and recent run summaries from that sketch. It proposes up to three passive steps.
Review each step's entities, provider, reason, and credential prerequisites.
Remove unnecessary steps before choosing **Run reviewed plan**.

The initial supported actions are local root-domain normalization and ThreatFox
domain/IP intelligence lookups. ThreatFox queries its provider database; these
actions do not probe the selected targets. New results do not automatically
become inputs to additional lookups. Each selected entity receives at most one
ThreatFox request per reviewed step, and normalization makes no target requests.

## Model configuration and evidence

The copilot reuses the application's configured Mistral or OpenAI provider and
your Vault key. Supported provider/model settings are `LLM_PROVIDER` and
`LLM_MODEL`; key names are `MISTRAL_API_KEY` and `OPENAI_API_KEY`. Selected graph
context and your question are sent to that provider. Vault values are never
included in evidence, and credential-like property fields are removed.

The local review setup uses GPT-6.1 Sol with medium reasoning effort:

```env
LLM_PROVIDER=openai
LLM_MODEL=gpt-6.1-sol
LLM_REASONING_EFFORT=medium
```

Add `OPENAI_API_KEY` to your Vault to enable model-backed runs. The reasoning
setting applies to OpenAI planning, summaries, and chat. It does not enable
additional execution tools or change the reviewed-plan workflow.

Without a configured model, the copilot offers type-based suggestions and factual
run summaries, explicitly labelled **no LLM used**. These suggestions do not
interpret the investigation question. Configured-provider failures are shown
as errors, so they do not look like successful model responses.

After execution, review the run statuses, outcome summaries, and result evidence.
Model summaries cite their run IDs. An empty result does not establish absence;
failed, partial, or truncated results require further review. You can save a
summary as a draft case finding, with its evidence references and review decision
set to pending.

## Reuse and permissions

**Save reviewed plan as flow** creates an ordinary flow recipe with input types
and independent enrichment branches. It does not store the original entity IDs
or values. It can be saved after execution, when enrichers have updated entity
versions. The normal flow editor and launch controls remain available.

Readers can generate plans and inspect accessible results. Running plans and
saving recipes require edit permission on the source investigation. The API
rechecks permissions, compatible entity types, selected IDs, and required key
presence. Execution also checks entity versions: if a collaborator changed a
selected entity after planning, generate a new plan before running it.

The copilot has no arbitrary code, shell, Cypher, or URL execution tools. Provider
and graph text is treated as evidence rather than instructions. Plans stay
bounded to their reviewed selection; graph arrangement and defensive searches
over imported telemetry are later capabilities.
